# 内存分配器

## 概述

只要内核开始管理“动态对象”（进程控制块、页表、文件句柄、缓冲区……），就需要一个内存分配器。

在 `no_std` 的学习型内核中，我们通常先实现一个 **最小可用** 的分配器，让后续子系统能跑起来，再逐步演进到更完整的方案（空闲链表、伙伴系统、页分配器等）。

本仓库在 `src/kernel/memory.rs` 实现了一个非常简单的 **bump allocator（指针递增分配器）**：

- 只维护一个 `next_free` 指针
- 每次分配把 `next_free` 向后挪动
- `deallocate()` 目前不回收（占位）

## bump allocator 的数据结构

`Allocator` 维护三个关键字段：

- `heap_start`：堆起始地址
- `heap_end`：堆结束地址
- `next_free`：下一块可分配地址

初始化时把 `next_free = heap_start`，随后每次分配做：

1. size 向上对齐（本仓库对齐到 8 字节）
2. 检查是否越界
3. 返回旧的 `next_free`，并更新 `next_free += aligned_size`

## 初始化：把“堆区”告诉分配器

在 `src/kernel/mod.rs` 的 `kernel::init()` 里，你可以看到：

- `memory::init_memory(0x2000_0000, 1024 * 1024);`

这相当于告诉分配器：

> 从 `0x2000_0000` 开始，有 1MB 连续内存可作为堆使用。

在真实内核里，这个范围一般来自：

- 引导加载器提供的内存布局
- 设备树（DTB）描述的 RAM 区间
- 内核链接脚本提供的 end 符号等

本项目为了简化，直接写死了一个地址范围。

## 分配与对齐

为什么要对齐？

- CPU 访问未对齐地址可能触发异常（取决于架构/配置）
- 对齐能提升性能，也方便后续把内存用于更复杂的数据结构

本仓库的对齐方式是：

```rust
let aligned_size = (size + 7) & !7;
```

这会把 size 向上对齐到 8 的倍数。

## 释放（deallocate）的“先占位”

本仓库目前的 `deallocate()` 不做任何事，这意味着：

- **内存不会被回收**
- 运行久了会“分配失败”

这对教学演示（跑通进程/页表/文件系统结构）通常够用，但如果你要做更接近真实 OS 的行为，需要引入可回收的分配策略。

## 相关辅助函数

`src/kernel/memory.rs` 还提供了一些在 `no_std` 环境里常用的“基础设施”：

- `memcpy(dst, src, size)`
- `memset(ptr, value, size)`
- `allocate_string(s)`：把字符串复制到堆上（演示用途）

这些函数在没有标准库时很常见（类似“迷你 libc”）。

- bump allocator 的核心思想与局限
- 为什么需要对齐
- `init_memory()` 如何把堆区交给分配器管理
