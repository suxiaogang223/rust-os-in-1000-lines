# 错误恢复

## 概述

错误恢复（recovery）并不等同于“吞掉错误继续跑”。在内核里，**安全与一致性**往往比“继续运行”更重要。

本节讨论在本教程范围内，面对不同类型错误时可采用的策略，并解释为什么早期内核通常只做“最小恢复”。

## 内核里的错误大致分三类

### 1) 可重试（Transient）

例如：

- 设备暂时忙（busy）
- 需要等待中断/事件

策略：重试、等待或返回错误码给上层。

### 2) 可隔离（Isolated）

例如：

- 某个用户进程非法访存
- 某个用户进程触发非法指令

策略：**终止当前进程**、回收资源，让系统其余部分继续运行。

### 3) 不可恢复（Fatal）

例如：

- 内核自身数据结构损坏
- 不应该发生的断言失败
- 关键内存管理状态不一致

策略：panic/停机，保留调试信息。

## 最小内核阶段的现实选择

在本教程的早期阶段，系统通常还没有：

- 完整的进程隔离
- 页表与权限控制（或尚不可靠）
- 完整的资源回收机制

因此，**最常见的策略是：打印足够信息 + 停机**。

本仓库目前也主要采用这种方式：

- panic 直接停机（见 `src/main.rs`）
- 异常处理里主要打印 `mcause/mepc/mtval`（见 `src/kernel/exception.rs`）

## 面向后续扩展的恢复策略

随着你逐步实现：

- 进程管理（第 07 章）
- 分页与内存保护（第 08/06 章）
- 用户态与系统调用（第 09/10 章）

你可以把恢复策略升级为：

- 用户态异常：kill 进程 + 记录退出码
- 系统调用错误：返回 `-EINVAL/-EBADF` 等错误码（约定好 ABI）
- 设备/IO 错误：上抛到文件系统或应用层处理

## 设计建议：先把“报错信息”打通

恢复策略的前提是“可观测性”。建议你优先保证：

- 串口输出稳定
- panic 信息完整
- trap 信息完整（cause/pc/mtval）

否则你很难判断“恢复是成功了，还是只是把错误隐藏了”。

## 小结

本章你应该掌握：

- 错误恢复的目标是“控制损害范围”，而不是无脑继续运行
- 早期内核优先做：打印 + 停机
- 随着隔离与资源管理完善，才能逐步做到：kill 单个进程、返回错误码等更细粒度的恢复
