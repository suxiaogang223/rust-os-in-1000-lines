# 上下文切换

## 概述

调度器选出了“下一个进程”，但 CPU 还在执行当前进程的代码。要真正切到另一个进程，需要 **上下文切换（Context Switch）**：

1. 保存当前进程的 CPU 状态（寄存器、PC、SP 等）
2. 恢复下一个进程的 CPU 状态
3. 跳转到下一个进程继续执行

上下文切换是 OS 的“硬核现场活”，通常需要少量汇编配合。

本仓库目前提供了进程结构与调度框架（`src/kernel/process.rs`），但“真实的寄存器保存/恢复”仍是后续扩展点。本节给出实现路线与最小骨架。

## 什么是“上下文”

对一个线程/进程来说，能继续执行所需的上下文通常包括：

- 通用寄存器 `x1~x31`（至少包括被调用者保存寄存器）
- `sp` 栈指针
- `pc` 程序计数器（或异常返回地址）
- 关键 CSR（如 `mstatus`、可能还有页表寄存器 `satp` 等）

最小实现可以先只保存一部分寄存器（教学演示），但要意识到：保存不完整会导致恢复后状态错误。

## 一个典型的实现分层

建议把上下文切换拆成两层：

1. **Rust 层**：决定切换时机、选择 next 进程、维护状态机
2. **汇编层**：负责原子地保存/恢复寄存器并跳转

Rust 层大致流程：

```text
cur = scheduler.current()
next = scheduler.pick_next()
save_context(cur)
restore_context(next)
return to next
```

## 触发方式：从“协作式”到“抢占式”

### 协作式（cooperative）

进程主动调用 `yield()` 系统调用让出 CPU：

- 好处：实现简单，不依赖定时器中断
- 坏处：如果进程不让出，系统会卡住

### 抢占式（preemptive）

定时器中断触发切换：

- 好处：更接近真实系统
- 坏处：需要完善的 trap 现场保存/恢复与中断确认

建议学习路线：先协作式跑通，再上抢占式。

## 与异常/中断的关系

在 RISC-V 上，抢占式切换往往发生在 trap 上下文：

- 定时器中断进入 handler
- handler 决定要切换
- 保存当前上下文到 `Process`（或专门的 `Context` 结构）
- 恢复下一个上下文
- `mret` 返回到新的 `mepc`

因此，上下文切换往往和第 04/05 章的异常/中断处理强相关。

## 小结

本章你应该理解：

- 调度选人，上下文切换负责“换人”
- 上下文切换通常需要汇编保存/恢复寄存器
- 推荐先做协作式切换，再做定时器抢占式切换
